# Рассылка с личного Telegram-аккаунта

Python 3.10+, Linux или macOS. Windows не поддерживается блокировкой `fcntl`.
Используется Telethon, не Bot API. Отправляйте только в чаты, где рассылки разрешены:
случайные интервалы не гарантируют защиту от ограничений Telegram.

## Безопасность перед переносом

В исходном проекте сессия `session.session` была сохранена в Git. Она даёт доступ
к аккаунту. Если репозиторий или файл передавались кому-либо, завершите эту сессию
в Telegram → Настройки → Устройства, затем авторизуйтесь заново.
Удаление файла из текущего Git не удаляет его из старых коммитов.
Не публикуйте историю репозитория с этой сессией; очистка истории и отзыв сессии —
отдельные действия владельца. API-реквизиты из старого исходника также остаются в истории.

Новая сессия хранится в `data/session.session`; старый файл в корне автоматически
НЕ используется. `data/`, `.env` и сессии исключены из новых добавлений в Git.
Сессию и резервные копии храните как секреты; не используйте один файл сессии
одновременно на нескольких серверах. Блокировка защищает только один общий DATA_DIR.

## Подготовка

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
cp .env.example .env
chmod 600 .env
```

Заполните `.env` своими `TELEGRAM_API_ID` и `TELEGRAM_API_HASH` с my.telegram.org.
Не оставляйте значения-заглушки. Уведомления отключены по умолчанию; для них
задайте `TELEGRAM_ADMIN_CHAT`. Это адрес получателя уведомлений, не разрешение управлять сервисом.

Для запуска через SSH загрузите переменные в окружение (файл `.env` — доверенный
shell-файл, исполняемый этой командой):

```sh
set -a
. ./.env
set +a
.venv/bin/python main.py check
.venv/bin/python main.py login
```

`login` запрашивает телефон, код из Telegram и при необходимости пароль 2FA.
Он сохраняет сессию и **не запускает рассылку**. Не передавайте код и пароль
через аргументы команд, Git или логи. Вход делайте под тем же пользователем и
с тем же DATA_DIR, что и будущий сервис.

```sh
.venv/bin/python main.py run
```

**Первая отправка — сразу.** Между отправками одна пауза 1–3 часа.
После последнего чата пауза 23 дня. Расписание и прогресс сохраняются атомарно;
перезапуск не обнуляет цикл. `run` не запрашивает авторизацию в фоне: при
недействительной сессии завершится с ошибкой и потребует отдельного `login`.

## Обновление материалов

Редактируйте через SSH/SFTP:

- `Материалы/chats.txt`: один адрес чата на строку, например `@groupname`.
  Пустые строки и строки с `#` игнорируются; дубли удаляются.
- `Материалы/message.txt`: текст подписи к альбому. Учитывайте ограничения Telegram.
- `Материалы/photos/`: минимум три непустых файла JPG/JPEG/PNG/WEBP.
  Отправляются первые три по сортировке имени. Это проверка наличия, не валидация изображения.

Перед **каждой отправкой** файлы перечитываются. Новые чаты будут добавлены в текущий
цикл, удалённые — не будут отправлены, уже обработанные адреса повторно не отправляются.
Используйте одинаковое написание адресов: разные адреса/алиасы одного чата не
распознаются как один получатель. Изменения не сокращают назначенную паузу, включая 23 дня.
Уже начатая отправка использует снимок текста и байтов фотографий.
Заменяйте файлы через загрузку во временное имя и переименование, а не записывайте
поверх во время чтения. Несколько файлов не образуют единую транзакцию:
для согласованного обновления всего комплекта остановите сервис, обновите и запустите.
Отсутствующие/неполные материалы не обнуляют прогресс; проверка повторяется через минуту.

Пути по умолчанию считаются от `main.py`, а не рабочего каталога. Можно задать
абсолютные `MATERIALS_DIR` и `DATA_DIR`. Каталог DATA_DIR должен быть постоянным,
доступным на запись только сервисному пользователю. Не удаляйте state.json ради перезапуска.

## Неопределённая отправка и ограничения

При `FloodWait` сервис сохраняет требуемую паузу и повторяет отправку позже.
При остальных ошибках отправки он консервативно останавливается: сообщение или
часть альбома могли уже уйти. Сначала остановите фоновый сервис, затем:

```sh
.venv/bin/python main.py status
```

Проверьте указанный в `in_flight` чат непосредственно в Telegram.

```sh
# Сообщение доставлено (либо принято решение пропустить этот чат):
.venv/bin/python main.py resolve --outcome sent
# Сообщение точно не доставлено; разрешить повтор после паузы:
.venv/bin/python main.py resolve --outcome retry
```

После исправления причины ошибки запустите сервис снова. При частичной доставке
проверяйте вручную: гарантии exactly-once у сетевой отправки нет.
`status` и `resolve` требуют остановленного сервиса, чтобы не читать/менять состояние
параллельно с работающим процессом.

## Linux: systemd

В репозитории есть `telegram-sender.service` для `/opt/telegram-sender` и пользователя
`telegram-sender`. Администратор должен создать этого непривилегированного пользователя,
разместить проект, создать venv, настроить владельца каталога и `.env`, выполнить `login`
под этим пользователем. При другом пути/пользователе измените unit.

```sh
sudo cp telegram-sender.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now telegram-sender
sudo journalctl -u telegram-sender -f
# Перед повторным login, status, resolve или согласованным обновлением:
sudo systemctl stop telegram-sender
```

После разрешения ошибки: `sudo systemctl start telegram-sender`.
Unit перезапускает процесс после ошибки через минуту, но незавершённую отправку
не повторяет автоматически. Проверяйте журнал: ошибки авторизации/отправки требуют оператора.
`.env` читается systemd как EnvironmentFile; используйте простые KEY=value без `export`.
Сервису нужен сетевой доступ к Telegram. Если сеть блокирует Telegram, нужен VPN
на сервере или отдельно настроенный транспорт; встроенной настройки прокси здесь нет.

## Проверки без Telegram

```sh
python3 -m unittest -v test_main.py
python3 main.py check
```

Тесты используют заглушки клиента и временные каталоги, не входят в аккаунт
и не отправляют сообщения. `check` читает материалы, но не открывает сессию.
